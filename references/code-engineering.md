# 九、编码工程层协议（code-engineering）

> 目标：治「新人重复造轮子」——AI 接到编码需求后，先查全球有没有成熟做法（库/基座/实践/同类产品），摆明「自研 vs 借力」再动手。
> v2.2.0 新增。本协议管编码类任务的触发判定、检索动作、评分标准与交付格式；检索防过期/防错误规则仍归 search-freshness 与 root-digging，执行动作归 search-execution。

---

## 1. 轮子判定器（触发分级，编码任务第一道闸）

接到任何编码需求，先判类，再决定是否触发成熟方案检索：

| 级别 | 判定 | 动作 |
|---|---|---|
| 🔍 强制检索 | 需求命中下方「通用功能清单」任一项 | 先检索成熟库 + 最佳实践，再写码 |
| 🏗 项目级检索 | 「做一个 App / 网站 / 系统 / 机器人 / 自动化工具」类整项目需求 | 先检索基座项目 + 脚手架 + 同类完整产品，再定架构 |
| ⚡ 跳过检索 | 纯业务逻辑编排（if/else 业务规则）、一次性胶水脚本、已有库的调用拼接、用户已点名技术方案 | 直接写，落款注明「未触发轮子检索：原因」 |

**通用功能清单（命中即 🔍）**：认证/登录/OAuth、支付、爬虫与抓取、Excel/PDF/Word 解析与生成、日期与时区、HTTP 客户端封装、ORM/数据库迁移、图片/文件处理、加密/压缩/哈希、图表/日历/上传等 UI 组件、推送/通知、定时任务/队列、批量导入导出、验证码/防刷、地图/定位。

判定口诀：**「这个功能，前人是不是肯定写过一千遍？」是 → 检索；「这是我业务独有的？」是 → 直接写。**

**判级兜底**：判级拿不准时**宁检索勿漏**——检索成本是分钟级，造错轮子的返工成本是小时级。新手口吻的模糊需求（如「做个爬虫」）默认按项目级处理。

**轮子记忆优先**：判定前先查既有轮子记忆（§6），命中且在有效期内直接复用，跳过检索。

## 2. 四类检索目标（MECE，逐类扫）

| 类 | 找什么 | 典型落点 |
|---|---|---|
| A 成熟第三方库 | import 即用的单点能力 | npm / PyPI / pub.dev / Maven |
| B 基座/脚手架 | 整体改造为自家项目的骨架 | GitHub 模板仓库、官方 CLI 脚手架 |
| C 最佳实践 | 「这个功能怎么写才对」的公认写法 | 官方文档、Stack Overflow 高票、权威博客 |
| D 同类完整产品 | 与需求几乎重合的开源实现 | GitHub 同类项目、Gitee、开源alternative 站 |

扫描顺序：D → B → A → C（先看有没有整车，再看骨架，再看零件，最后看装配手册）。任一类找到「直接可用且评分达标」的方案即可提前收窄，不必四类扫满。

## 3. GitHub 深度搜索动作（本协议专属执行层）

**执行绑定（防空转，v2.3.0）**：GitHub 搜索语法必须落到 AI 实际可用的工具上，规则不绑定动作即空转（v2.1.0 教训）：

1. **首选 GitHub API**（WebFetch 直抓，结果为结构化 JSON，无反爬风险）：
   `https://api.github.com/search/repositories?q=<关键词>+stars:>200+pushed:>2026-01-01&sort=stars&per_page=10`
   （`q` 中空格用 `+`、冒号用 `:` 原样；匿名限流 10 次/分钟，超限即降级到第 2 步，禁止重试轰炸）
2. **次选网页直抓**：WebFetch `https://github.com/search?q=<关键词>+stars%3A%3E200&type=repositories`
3. **再降级**：普通 WebSearch `site:github.com <关键词>`；中文需求加搜 Gitee。
4. **awesome 清单**：WebFetch 抓 `https://github.com/topics/<领域>` 或搜索 `awesome <领域>`，清单项目优先入候选。
5. **候选 R1 核查**（每个候选必须 WebFetch 其 README 页/仓库主页）：Star 数、最近 commit 时间、open issues 数量与维护者响应、License 文件、文档入口。摘要数字不算数，以正文为准。
6. **候选数量纪律**：进入评分的候选 3～5 个，不超 5；一类扫完无合格候选即记录「该类空手」，转下一类。

## 4. 五维评分标准（100 分制，新人加权）

| 维度 | 权重 | 打分规则 |
|---|---|---|
| 维护活跃度 | 30 | 最近 commit ≤6 个月 = 30；6～12 个月 = 15；>1 年 = 0 且触发一票否决复核 |
| 文档友好度 | 25 | README 完整 + 有 Quickstart/示例 = 25；有文档但晦涩 = 15；几乎无文档 = 5；有中文文档或教程丰富 +5（上限 25） |
| 成熟度 | 20 | 库类 Star ≥1k / 应用类 ≥500 = 20；100～1k = 12；<100 = 5（「完成态」小工具如 CLI 可豁免低 Star，按维护+文档给分） |
| 场景契合度 | 15 | 技术栈匹配 + 核心需求原生覆盖 = 15；需插件/包装 = 8；需大改 = 3 |
| License | 10 | MIT / Apache / BSD = 10；LGPL / MPL = 5；GPL / AGPL = 0 且强制商用警示；未标注 = 0 且进否决复核 |

**一票否决（直接出局，不进对比表）**：仓库已归档（archived）；>1 年无维护且属「持续演化型」工具（框架/SDK 类，非完成态）；License 缺失且用户场景涉商用。

**打分证据纪律（防伪精确，v2.3.0）**：每个候选的每个维度分数必须附一句证据引用，格式「25（README 含 Quickstart + 有中文教程）」。给不出证据引用的维度按最低档计分。宁用粗档+证据，不用细档+拍脑袋。

**AI 友好度加成**：主流库（训练数据丰富）AI 生成代码质量显著高于冷门库——这算进「成熟度」维度的实际价值，理由可在对比表中注明。

**供应链安全（v2.3.0）**：推荐第三方包前必须执行：
- 包名与 PyPI / npm 官方页面（`pypi.org/project/<名>` / `npmjs.com/package/<名>`）**逐字核对**，防 typosquatting（`request`≠`requests`、`coloroma`≠`colorama`）
- 查看周下载量：周下载 <1 万的包在对比表中标注「小众，建议谨慎」
- 陌生包（无大厂/知名组织背书）须附一句「为什么信它」（维护者身份/审计记录/高星依赖方）

**分数解释**：≥75 强烈推荐；60～74 可用，注明短板；<60 仅作参考，倾向自研或换道。

## 5. 交付格式（列表对比，用户拍板）

```
【结论先行】推荐 <方案X>（X/100），一句话理由。
【对比表】候选 ×（评分/类型/核心优势/核心风险/License）
【自研 vs 借力】借力：说明用法（import / fork 改造 / 仅参考架构）；
          若结论是自研：必须给出「为何现成方案都不合适」的具体理由。
【等你拍板】A/B/C 选择项。
```

- 用户拍板前**不写业务代码**；用户说「你自己定」时取最高分并附理由直接开工。
- 落款继承引擎四行版，信息缺口常例：某类候选未找到 / License 待确认 / 仅凭 README 未实测。

## 6. 轮子记忆（检索结论沉淀，v2.3.0）

检索结论必须沉淀复用，防止同类需求反复重查：

**写入**：每次拍板完成后，把结论写入工作区记忆文件（`memory/` 下当日日志或 MEMORY.md）：

```
[轮子记忆] <需求领域，如 Excel解析> → <选定方案，如 openpyxl> · <验证日期 YYYY-MM-DD> · <一句话结论，如 v3.1 可用，合并单元格写入正常> · <有效期至 YYYY-MM-DD>
```

**读取**：轮子判定器（§1）判定前先扫记忆，命中且在有效期内 → 直接复用，跳过检索，落款注明「复用轮子记忆：<领域>，记录于 <日期>」。

**有效期**：默认 6 个月；框架/SDK 类（演化快）3 个月；到期或复用时发现方案不好用 → 失效，重新走完整检索。

**回写校准（闭环）**：使用推荐方案过程中——
- 遇到协议没预料到的坑（文档误导/隐藏 bug/兼容问题）→ 回写记忆更新结论，必要时在下一轮对比表中给该候选降分
- 严重翻车（安全漏洞/维护者跑路）→ 写入黑名单行 `[轮子黑名单] <包名> · <原因> · <日期>`，永久出局
- 用得顺 → 更新验证日期延长有效期

## 7. 与既有协议的合并执行

- 流程顺序：轮子记忆检查（§6）→ 轮子判定器（§1）→ 四类扫描（§2）+ GitHub 深度搜索（§3，作为 search-execution §3 直达表的开源品类扩充）→ R1 核查（search-execution §2）→ 供应链安全核对（§4 附则）→ 五维评分（§4）→ 交付等拍板（§5）→ 轮子记忆写入（§6）。
- 时效规则继承：版本号、Star 数、commit 日期一律带检索日期标注（对应 search-freshness 时间锚点）。
- 冲突裁决：防过期/防错误判定以 search-freshness / root-digging 为准；本协议只管编码场景的「找什么、怎么评、怎么交」。
