# 六、联网检索 · 时效核查协议（search-freshness）

> 目标：杜绝「AI 给了过期方法，用户照做浪费几小时」。本文件是所有联网检索场景的可判定规则库——每条规则都是 `if 条件 then 必须动作`，不是原则口号。SKILL.md 的研究类条款与 learning.md 的横纵分析法、事实核查模板均引用本协议。

---

## 1. T0 十秒分类（搜索开始前必做）

先问一句：**「这个答案 12 个月后还会有效吗？」**

| 类型 | 判定 | 处理 |
|---|---|---|
| **敏感型** | 软件/命令行/API 操作、安装配置教程、价格费率、平台政策、活动优惠、版本兼容、界面操作路径 | 走完整验证（第 2 节五步）+ 红绿灯 + 预验 |
| **钝感型** | 概念定义、数学原理、历史事实、方法论 | 只需标注来源与日期，不做重验证 |

**兜底规则：凡「怎么装 / 怎么写 / 怎么配」的 How-to 问题且涉及具体工具或平台，一律按敏感型处理。**拿不准时按敏感型执行。

## 2. 敏感型五步时效验证（按序执行，任一步失败即降置信度）

1. **官方锚点**：查官方文档 / changelog / release notes，记录该方法对应的版本号与当前最新稳定版本；
2. **失效扫描**：搜「产品名 + deprecated / breaking changes / sunset / 下线 / 迁移公告」；
3. **社区验尸**：搜「方法名 + error / not working / 失效 + 当前年份」，重点查近 6 个月的 GitHub issues 与 Stack Overflow 是否有人报错；
4. **双源日期**：至少 2 个独立来源，取最新日期；最新来源超过 12 个月且该领域迭代快，置信度直接降一级；
5. **落款**：方法类答案必须附「✅ 验证于 YYYY-MM，适用 vX.Y」。无落款视为不合格输出。

## 3. 反过期硬规则 R1～R5（针对 AI 搜索真实失效模式）

- **R1｜禁止摘要定稿**：涉及「怎么装 / 怎么写 / 参数 / 命令」的操作性结论，必须至少打开 1 个原文链接核对正文日期与版本号。只凭搜索结果摘要写结论视为违规——这是过期答案的第一大成因。
- **R2｜旧文霸屏重搜**：搜索结果前 3 条发布时间集中在同一旧年份、或全部无日期时，必须追加年份限定词（如加「2026」）重搜一次。
- **R3｜版本先行**：写任何 API / 命令前，先查官方 changelog 或 release notes 确认当前稳定版本；结论标注「适用于 vX.Y，核查于 YYYY-MM」。查不到版本号就如实写「版本未核实」，禁止默认最新。
- **R4｜易变字段强制落款**：价格、配额、默认值、模型名等易变信息，一律就近标注来源与日期，禁止作为无标注的稳定事实陈述。
- **R5｜冲突以官方为准**：同一操作在官方文档与博客结论冲突时，以官方文档为准；博客仅作补充并说明分歧点。

## 4. 强制追加搜索的触发条件

第一轮搜索后出现任一信号，必须再搜一轮（上限 2 轮）：

1. 全部来源为二手博客 / 教程站 / 营销页，零官方一手来源；
2. 最新来源距今超过 12 个月（敏感型超过 6 个月）；
3. 来源间结论矛盾，且无法用版本差异解释；
4. 多个结果内容雷同，实为同一篇文章转载（单一来源伪装成多来源）；
5. 出现「已下线 / 改名 / 迁移」线索但无官方确认。

追加策略：官方术语与社区俗称互换、改搜英文关键词、直接搜报错信息原文、直查 GitHub issues 与 release notes。2 轮后仍无果 → 按「失败兜底」（第 7 节）处理。

## 5. 中文搜索特化（命中即切英文重搜）

中文技术圈天然滞后一个版本以上，且转载农场严重。命中任一条，立即切换英文关键词 + `official docs / changelog / github issues` 重搜：

1. 结果 ≥2 条来自 CSDN / 博客园 / 公众号且内容互相雷同（转载农场特征）；
2. 查询对象是版本号、release note、API 参数、报错信息；
3. 中文结果可辨认日期全部落后当前 ≥1 年。

切英文后仍找不到 → 回退到官方文档站内搜索，而不是回退采用过期的中文结果。

## 6. 分级投入 L0～L3（防过度搜索）

| 级别 | 适用问题 | 动作 |
|---|---|---|
| L0 不搜 | 定义、概念、数学、语法 | 训练知识足够，不联网 |
| L1 单轮 | 查最新版本号 / 价格 / 新闻 / 任职 | 一次定向搜索官方源即可 |
| L2 两轮 | 操作教程类 How-to | 首搜 + 触发第 4 节条件时补一轮验证 |
| L3 多轮交叉 | 横纵分析、事实核查、生产环境 / 破坏性操作 | ≥3 轮、≥1 个一手来源、多源交叉后才允许出结论 |

判定口诀：**答案会随时间变的才搜；变了会害人的才多搜。**

## 7. 输出格式规范

### 时效红绿灯（敏感型问题的第一行，先于一切正文）

```
🟢 已核实 2026-08，匹配 vX.Y
🟡 来源 2025-03，可能过期｜动手前先做下方预验
🔴 未找到近期可靠来源，方法大概率已变，仅供参照
```

判定标准：🟢 = 6 个月内来源且版本已对上；🟡 = 6～18 个月或版本未确认；🔴 = 18 个月以上或有界面大改线索。钝感型问题与 🟢 且无风险的普通答案零标注，保持干净。

### 30 秒预验（🟡/🔴 答案必带，插在第一个高危步骤前）

格式三件套：无害命令 + 输出对照 + 不匹配时的出口。命令必须只读、零副作用：

```
⏱ 动手前先跑 `xxx --version`：
→ 显示 v2.x：下面流程适用
→ 显示 v3.x：停下回我一句「v3」，我换流程
```

其他预验形式：检查某个菜单项是否还在、某个路径是否存在。

### 环境「猜-改式」声明（给操作步骤前）

自设环境并声明，用户不对时纠正一句即可，不连环追问：

```
以下步骤默认此环境，不符请纠正：Windows 11｜v3.2 官网版｜默认路径
```

关键分叉点双写两个版本的差异，不全文双版本。

### 失败兜底（搜不到当前有效答案时的诚实输出）

```
没搜到 YYYY 年的可靠教程，以下是 YYYY-MM 的旧方法：
✅ 大概率仍有效：第 1、3 步（基础部分极少变）
⚠️ 大概率已变：第 X 步（新版改了 XX）
🛣 自行求证的出路：官方迁移文档 [链接]／运行 `xxx --help` 看现行参数
动手前先做上方 30 秒预验。
```

禁止把旧方法包装成现答案。「没搜到」必须明说——诚实比硬答可信得多。
