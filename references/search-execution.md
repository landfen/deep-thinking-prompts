# 八、联网检索 · 执行层协议（search-execution）

> 目标：把 search-freshness（防过期）与 root-digging（防错误）的**规则**落到**具体动作**上。规则回答"该做什么"，本协议回答"用什么、怎么搜、搜不到时往哪走"。凡进入第二层检索流程的任务，本协议与时效/刨根两协议**同时生效**。
> v2.1.0 新增，源自 v2.0 复盘：协议规则完备但未绑定执行工具，导致"必须打开原文核对"（R1）类规则实际空转、首轮搜索串行低效、时间锚点依赖事后补救（R2）。v2.2.0 官方直达表扩充开源方案品类（对接第五层编码工程层）。

---

## 1. 首轮并行搜索（敏感型强制，钝感型可选）

敏感型问题（T0 判定）首轮**必须**同时发起 3～4 路并行搜索，禁止串行逐个试：

| 路 | 查询构造 | 目的 |
|---|---|---|
| ① 中文路 | 中文关键词 + 当前年月（如「xxx 安装 2026」） | 本土语境与中文一手源 |
| ② 英文路 | 英文关键词 + `official docs / changelog / github issues` | 突破中文圈滞后一个版本 |
| ③ 官方定向 | 直接抓取官方文档 / changelog / releases 页（见第 3 节直达表） | 一手来源，绕过搜索引擎中转损耗 |
| ④ 社区定向 | 「产品名 + error / not working + 年份」，直查 GitHub issues / Stack Overflow | 社区验尸（对应时效五步第 3 步） |

- **时间锚点前置**：所有查询词构造时即带时间限定（年份，敏感型加年月），不等 R2 旧文霸屏触发后再补。
- 钝感型（L1 单轮足够）可只走 ①+③ 两路。
- 并行发起后统一汇收结果，再按 root-digging 第 2 节渠道多样性规则筛源。

## 2. R1 落地：打开原文 = 抓取正文，不是看摘要

- 「打开原文链接核对」的**执行定义**：对关键来源执行网页正文抓取，核对页面内文日期与版本号，搜索结果摘要仅用于初筛排序。
- **摘要引用违规判定**：操作性结论（怎么装/怎么写/参数/命令）若仅凭摘要写成，即违反 R1。抽查方式：结论里每个版本号、日期、参数值都能指回某次正文抓取。
- 正文抓取后页面无日期标注的，按 search-freshness §7 规则视为来源日期不明，置信度降级处理。

## 3. 官方直达表（优先直抓，不经搜索引擎中转）

常见品类的官方一手入口构造规则，检索时**优先直接抓取**，搜索引擎仅作发现未知站点的补充：

| 品类 | 直达入口构造 |
|---|---|
| 软件版本 | `github.com/<org>/<repo>/releases`、官网 `/changelog`、`/release-notes` |
| API 参数 | 官方文档站 `/docs/<product>/api`，站内搜索优先于全网搜索 |
| 价格/套餐 | 官网**购买页/定价页**（P2 最高等级信源），而非帮助中心 |
| 政策/活动 | 官方公告页、新闻稿栏目，核对页面标注的发布日期 |
| 报错信息 | 直接搜报错原文（英文优先），叠加 GitHub issues 站内搜索 |
| 开源方案/库 | GitHub 搜索语法（`stars:>200 pushed:>YYYY-MM-DD language:<栈>`）+ `awesome <领域>` 清单 + Gitee（中文需求），详见 code-engineering §3 |

- 直达失败（403 / 521 / 反爬）时的降级顺序：换镜像站 → 搜索引擎快照 → 社区转载源（须标注"非一手，待核"）。

## 4. 追加搜索升级路径（阶梯式，上限 3 轮）

第一轮未取得合格证据（触发 search-freshness 第 4 节任一条件）时，按阶梯升级，不许原地重复换词：

| 轮次 | 动作 |
|---|---|
| 第 2 轮 | 切英文重搜（复用 search-freshness §5 联动）+ 换渠道类型（官方↔社区↔媒体互换补缺） |
| 第 3 轮 | 官方站内搜索 / 直链抓取（第 3 节直达表）/ 搜报错原文 / 查 release notes 与 issues |
| 3 轮后仍无 | 走失败兜底（search-freshness §7），禁止把低置信答案包装成确定结论 |

> v2.0 及之前的"上限 2 轮"收紧为阶梯化 3 轮：每轮必须**换路数或换渠道类型**，纯重复换同义词不算一轮。

## 5. 证据日志（全程留痕，落款的依据）

每次正文抓取/关键检索即时记一行，格式统一：

```
[来源标题 · 日期 YYYY-MM-DD · 类型(官方实时页/官方公告/官方文档/媒体/社区/百科) · 一句话结论]
```

规则：
- **一事一行**，不写长文；一句话结论必须与最终答案中的具体论断对应
- **同源快照扩散**：转载/雷同来源只记首条，其余合并计数为 1（执行 P3 规则）
- **类型标注**直接映射 P2 信源等级，冲突裁决时按类型排序
- 落款「信息缺口」必须能从日志反推：日志里缺什么 = 缺口是什么；日志空行较多 = 检索投入不足的信号
- 🟡/🔴 级交付时，日志随证据清单一并输出（紧贴落款前，不超过 10 行，超出只列关键源）

## 6. 与既有协议的合并执行

- **流程顺序**：T0 分类（search-freshness §1）→ 本协议第 1 节并行首轮 → R1 正文抓取（本协议 §2）→ 渠道多样性交叉（root-digging §2）→ 证据日志（本协议 §5）→ 红绿灯落款（root-digging §4）。
- **本协议不新增判停规则**：投入分级（L0-L3）、触发条件、置信度标准均以 search-freshness 与 root-digging 为准，本协议只管执行动作。
- 冲突时以两个协议文件的判定规则为准，本协议的执行动作服务于它们。
